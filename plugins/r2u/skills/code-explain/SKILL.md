# 代码讲解

## 目标

先用最小且有用的范围讲清楚代码，再按需扩展上下文。

## 工作流

1. 识别目标。
   - 优先使用用户明确指定的文件、函数、代码块或 diff。
   - 如果目标不明确，先解释最可能的范围，并说明你的假设。
2. 先只读相关代码，只有必要时再向外扩展上下文。
3. 按以下顺序解释。
   - 它做什么
   - 它如何工作
   - 它为什么存在，或者这次改动改了什么
   - 风险、边界情况、依赖关系
4. 使用具体引用。
   - 提到文件路径
   - 必要时提到符号、函数、类和关键行
5. 除非用户要求更深入的讲解，否则保持简洁。

## 输出风格

- 先用一句话概括。
- 对步骤多、结构复杂的内容，用项目符号拆开讲。
- 区分“代码事实”和“推断”。
- 如果代码明显有问题，直接指出并解释原因。

## 输出模板

按下面的顺序组织回答：

```text
一句话结论：这段代码/这个文件/这次改动的核心作用是什么。

它做什么：
- 说明入口、主要流程、关键分支和最终结果。

它怎么工作：
- 按执行顺序解释关键函数、变量、调用关系和数据流。

为什么这样写 / 这次改了什么：
- 说明设计意图、依赖关系、与上下文的联系。

需要注意的点：
- 列出边界情况、潜在 bug、隐含假设或可改进点。
```

## 何时展开更多细节

- 涉及多个文件
- 代码有不明显的控制流
- 用户问的是“为什么”或“怎么做”，而不只是“是什么”
- 改动触及 hook、脚本或工作流逻辑
